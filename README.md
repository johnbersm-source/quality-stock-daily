# quality-stock-daily

한국(KR) 1종목 + 미국(US) 1종목의 우량주 스코어카드(v3, 8블록 100점 + 2게이트)를
매일 계산해 PDF 리포트로 만들고 텔레그램으로 전송하는 자동화 파이프라인.

## 방법론

⚠️ 정정(2026-09-29): 코드 주석·문서 곳곳이 "`config/weights.yaml`에 전체
스코어카드 정의가 있다"고 적어왔는데, 실제로는 그런 파일이 저장소에 존재한
적이 없다 — 8블록 채점 로직은 처음부터 `src/scoring/blocks.py`·`gates.py`·
`dcf.py`·`models.py`에 Python 코드로 직접 구현돼 있고, `weights.yaml`은 그
설계의 "개념적 출처"를 가리키는 표현이 파일 참조처럼 굳어진 것뿐이다(런타임에
그 경로를 읽는 코드도 없음). 원본 아이디어는 "실전경제학 리서치 Vol.1"의
10항목 100점 스코어카드이며, v3는 그중 서로 겹치는 항목은 계승하고,
스트레스테스트(D블록)·안전마진(게이트)·거시(H블록)를 신설 추가했다. 두
게이트(`stress_test_gate`, `margin_of_safety_gate`) 중 하나라도 미통과면
8블록 총점과 무관하게 최종 등급이 "관찰"로 강등된다.

**미해결**: 원본 PDF("실전경제학 리서치 Vol.1") 자체가 이 저장소/세션
어디에도 남아있지 않아서, "PDF 원본 10항목 점수 vs v3 8블록 점수"를 리포트에
나란히 비교해서 보여주는 기능은 아직 설계도 못 한 상태다 — 리오님이
2026-09-29에 리포트를 보고 이 항목 부재를 지적함. 재구현하려면 원본 PDF를
다시 첨부받아 10항목 배점·기준을 추출하는 작업이 선행돼야 한다.

## 후보군 생성 방식 (2026-09-28, 정적 리스트 → 동적 생성으로 전환)

**이전에는 `config/watchlist.yaml`에 KR 23종목 + US 24종목을 손으로 큐레이션해
고정 리스트로 박아뒀었다.** 리오님 지시로 이 방식을 폐기했다: *"후보종목을
미리 선정해서 하는게 아니라 매일 보고서를 만들어 보낼때 그 시간 기준으로
해당되는 기업을 선정해서 보고서를 맞춰서 작성해야해."* 이제 `src/universe.py`가
**매 실행마다 그 시점 기준으로 후보군을 새로 조회**한다:

- **KR**: 원래 목표는 공식 KOSPI200+KOSDAQ150 지수 구성종목이었으나, (1) 공식
  KRX Open API(`openapi.krx.co.kr`, 이미 승인받은 `KRX_AUTH_KEY`)에는 지수
  구성종목 조회 기능 자체가 없고, (2) 실제 구성종목은 `data.krx.co.kr`의
  비공식 내부 API에서만 나오는데 이 경로는 2024-12-27부터 로그인(KRX_ID/PW)이
  의무화됐다(봇탐지 목적) — 매일 GitHub Actions에서 개인 계정 로그인을
  자동화하면 계정 제한/정지 위험이 있어(`krx_collector.py`가 애초에 이 문제
  때문에 pykrx 방식을 버리고 공식 API로 재작성된 전례와 동일한 이유), 대신
  **코스피 시가총액 상위 200 + 코스닥 시가총액 상위 150**을 대리 지표(proxy)로
  쓰기로 확정(2026-09-28, 리오님과 합의). 이미 승인된 공식 API만 쓰므로 추가
  키·로그인 불필요.
- **US**: S&P500 실제 구성종목(위키피디아 "List of S&P 500 companies" 공개
  표를 스크래핑, 대리 지표 아님) 전체 ~500종목. 이 세션에서 503개 확인,
  BRK.B → BRK-B 등 yfinance 호환 티커 정규화까지 실측 검증 완료.

파라미터(`top_n_kospi`/`top_n_kosdaq`)는 `config/pipeline.yaml`에서 조정 가능.

### ⚠️ 규모 확대에 따른 실행시간/API 호출량 리스크 → 2026-09-29 1차 실전 실행으로 부분 확인

후보군이 47개(KR 23+US 24)에서 **KR ~350개 + US ~500개 = 총 ~850개**로 늘어난
뒤 처음으로 `daily-report.yml`을 실제 실행(수동 `workflow_dispatch`,
run id 36556135779)한 결과:

- **실행시간: 9분** (90분 타임아웃 대비 크게 여유 — 우려했던 것보다 훨씬 빠름).
  Actions 분 소모량도 매일 이 정도면 무료/일반 플랜 월간 한도 내에서 충분히
  감당 가능한 수준으로 보인다.
- **US(503종목): 완전 성공.** 종목당 평균 ~0.8~0.9초로 순조롭게 진행, 2개
  종목이 게이트 통과, 최고점 AES Corporation(26.31점) 선정 → PDF 생성 →
  텔레그램 전송까지 정상 완료. 우려했던 yfinance rate limit(과거 24종목
  테스트에서 429 경험)은 이번 503종목 규모에서는 발생하지 않았다.
- **KR(350종목): 후보군 생성 자체가 실패.** `get_kr_candidates()`가 날린 첫
  KRX API 호출(`sto/stk_bydd_trd`)부터 곧바로 HTTP 429가 발생, 당시
  재시도 예산(6회, 지수백오프 cap 30초) 소진 후에도 계속 429 → KR 전체가
  후보군 생성 단계에서 스킵됨(KR 없이 US만 발송된 이유). 같은 날 앞서 여러
  진단 워크플로가 같은 KRX_AUTH_KEY로 반복 호출한 게 누적 원인일 가능성이
  높지만, 그날 총 호출량이 문서화된 일일 10,000건 한도보다 훨씬 적어 확정할
  근거는 없다(단정 대신 `krx_collector.py` 상단에 관찰 사실만 기록).
  **조치**: 재시도 예산을 늘림(`max_retries` 5→8, backoff cap 30→45초,
  jitter 확대) — 커밋 완료. 다음 실제 스케줄 실행(하루의 첫 호출)에서
  재현 여부를 재확인해야 하고, 그래도 반복되면 KR 후보군 조회를 하루 중
  다른 워크플로와 분리된 시간대에만 돌리거나 사전 스크리닝(후보 수 축소)이
  필요하다.

## 종목 선정 방식 (2026-09-28 확정)

매일 `src/universe.py`가 그 시점 기준으로 동적 생성한 후보군 전체를 v3
스코어카드로 채점 → `stress_test_gate`·`margin_of_safety_gate`를 모두 통과한
종목 중 최고점을 그날의 픽으로 선정. 최근 10일(기본값,
`config/pipeline.yaml`의 `selection.cooldown_days`로 조정 가능) 내 이미
픽으로 나온 종목은 후보에서 제외. 게이트 통과 종목이 하나도 없으면 픽 없이
"오늘은 통과 종목 없음" + 점수 상위 3개를 참고용으로만 병기(억지로 픽을
만들지 않음). 로직은 `src/selection.py`, 기록은 `data/pick_history.json`.
